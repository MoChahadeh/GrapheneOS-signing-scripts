# Memory Primitives, Metadata Isolation & MPK — Audit Findings

Audit target: GrapheneOS `hardened_malloc` @ commit `9e88c14`
Subsystem: low-level memory primitives, address-space reservation/layout, metadata isolation & guard regions, Memory Protection Keys (MPK/pkey) sealing, initialization, and fork safety.
Reviewer posture: authorized, defensive source audit. Default build configuration (`config/default.mk`) assumed unless noted.

## Subsystem Overview

The memory subsystem is small, disciplined, and clearly written. The relevant pieces are:

- **`memory.c` / `memory.h`** — thin wrappers around `mmap`, `munmap`, `mprotect`/`pkey_mprotect`, `mremap`, and `madvise`. Every wrapper enforces the policy that any error other than `ENOMEM` is fatal (`fatal_error`), and `ENOMEM` is reported to the caller as a `NULL`/`true` failure indicator. New mappings are created `PROT_NONE` (or `PROT_MTE` on ARM MTE builds); usable space is later unprotected explicitly.
- **`pages.c` / `pages.h`** — `allocate_pages` / `allocate_pages_aligned` / `deallocate_pages` build guarded mappings: reserve `usable + 2*guard` as `PROT_NONE`, then unprotect only the usable middle. All size arithmetic uses `__builtin_add_overflow` and `align()`. `page_align` and `PAGE_CEILING`-style rounding live here.
- **`h_malloc.c`** — the address-space layout and lifecycle:
  - The slab region (`slab_region_size`, default ≈ 12.25 TiB) is reserved up front as one giant `PROT_NONE` mapping (`init_slow_path`, h_malloc.c:1295) and carved into per-arena/per-size-class sub-regions, each with a randomized intra-region gap.
  - All writable allocator state lives in a single out-of-line `struct allocator_state` (h_malloc.c:1004) reserved with a high-entropy randomly-sized guard region on both sides (h_malloc.c:1270-1274).
  - The only global writable state is the `ro` union (h_malloc.c:70-85), which holds *pointers* into `allocator_state` plus the pkey; it is made read-only with `mprotect` after init (h_malloc.c:1332).
  - Metadata sealing via MPK is implemented by `thread_seal_metadata`/`thread_unseal_metadata` (h_malloc.c:1188-1196) wrapping `pkey_set`, applied coarsely at the public-API boundary. **Disabled by default** (`CONFIG_SEAL_METADATA := false`).
  - Fork safety via `pthread_atfork(full_lock, full_unlock, post_fork_child)` (h_malloc.c:1340).

Overall the isolation model is sound and the implementation matches the documented claims closely. Findings below are dominated by design-tradeoff observations and defense-in-depth notes; I found no memory-safety bug in this subsystem.

## Findings

### MEM-01 — MPK metadata sealing is disabled by default; the default posture relies entirely on out-of-line isolation + guard entropy
- **Severity:** Informational / Low
- **Type:** Design limitation (documented tradeoff)
- **Location:** `config/default.mk:5` (`CONFIG_SEAL_METADATA := false`); `util.h:87-95`; `h_malloc.c:1179-1196`
- **Description:** When `CONFIG_SEAL_METADATA` is false (the default, and the configuration shipped on GrapheneOS/Android, which uses ARM MTE instead), `USE_PKEY` is undefined and every `thread_seal_metadata`/`thread_unseal_metadata` compiles to a no-op (h_malloc.c:1179-1196 bodies are `#ifdef USE_PKEY`). Consequently, the writable `allocator_state` region (slab metadata bitmaps, canary values, region hash table, RNG state, free/quarantine lists) is plain read-write for the whole process lifetime. An attacker with an arbitrary-write primitive who can *locate* the metadata region can corrupt it directly, bypassing canaries and the free-validation logic.
- **Security Impact:** The confidentiality/integrity of metadata in the default build rests on the attacker not knowing the metadata region's address. That address is high-entropy (see Verified Strengths and MEM-02), and `ro` is read-only so leaking the library base does not leak the metadata pointer — so this is a reasonable posture, but it is a single line of defense (address secrecy) rather than two. On x86_64 GrapheneOS where MTE is unavailable, enabling MPK would add genuine hardening at a performance cost the project judges not worthwhile.
- **Recommendation:** This is an intentional, clearly-documented tradeoff (README.md:415-416, 275-281). No change required. Downstream integrators on x86_64 who can absorb the cost should consider `CONFIG_SEAL_METADATA := true`. Honest assessment: the cost/benefit call is defensible given the address-secrecy and read-only-pointer design.

### MEM-02 — Per-size-class slab gap is bounded by the *unused* tail of `REAL_CLASS_REGION_SIZE`, not by `REAL_CLASS_REGION_SIZE` itself
- **Severity:** Informational
- **Type:** Design limitation (inherent to fitting a class region inside its 2× envelope)
- **Location:** `h_malloc.c:1310-1312`
- **Description:** Each size-class region is placed at `arena_base + REAL_CLASS_REGION_SIZE*class + gap`, where `gap = (uniform(0, (REAL_CLASS_REGION_SIZE - CLASS_REGION_SIZE)/PAGE - 1) + 1) * PAGE`. Because `REAL_CLASS_REGION_SIZE == 2*CLASS_REGION_SIZE`, the gap ranges over up to `CLASS_REGION_SIZE - PAGE` (≈ 32 GiB), giving ≈ 23 bits of slot entropy. This is by construction: the class region must still fit in the remaining `REAL - CLASS` space after the gap. The base of each class region is therefore *not* uniformly distributed across the full 64 GiB envelope — it is uniform across the first 32 GiB.
- **Security Impact:** Minor. 23 bits of base entropy per size class is strong and there are no low-entropy deterministic offsets between size classes (each has an independent random gap). The slab region's outer guard relative to other mappings is the 12 TiB unmapped envelope plus ASLR of the whole region. No concrete weakening.
- **Recommendation:** None required; the ≈ 23-bit per-class entropy and absence of deterministic inter-class offsets satisfy the claimed property (README.md:426-428). Documented here only so the entropy figure is not over-stated as “full 64 GiB.”

### MEM-03 — Transient read-write window on the `ro` struct in `h_malloc_disable_memory_tagging` (ARM MTE builds only)
- **Severity:** Low
- **Type:** Design limitation / defense-in-depth
- **Location:** `h_malloc.c:2268-2297` (specifically the `memory_protect_rw(&ro,...)` … `memory_protect_ro(&ro,...)` window at 2279-2285)
- **Description:** `h_malloc_disable_memory_tagging` (compiled only under `HAS_ARM_MTE`) re-enables write access to the entire `ro` page, sets `ro.is_memtag_disabled = true`, then re-protects it read-only. The "read-only after init" invariant is therefore briefly violated at runtime. The window is minimized correctly: it is held under `full_lock()` (which also takes every size-class and region lock, h_malloc.c:1198-1207), it wraps a single one-byte store, both protect calls are fatal-checked, and the function is `COLD`. The early-boot `else` branch (h_malloc.c:2288-2291) writes the flag while `ro` is *still writable* (init has not yet run `memory_protect_ro`), serialized against init via `init_lock`.
- **Security Impact:** An attacker who already has a controlled write primitive *and* can win this narrow, lock-protected, MTE-only window could flip other `ro` fields (e.g. `slab_region_start`, `region_allocator`). This is a very constrained race and requires a pre-existing strong primitive plus precise timing; it does not by itself grant anything. It is strictly weaker than the always-writable metadata in the default (non-MPK) build (MEM-01), so it changes nothing about the default threat model.
- **Recommendation:** Acceptable as-is. If desired as defense-in-depth, the MTE-disable flag could live in `allocator_state` (already RW under MPK / write-protected only by isolation) rather than in the read-only `ro` page, eliminating the runtime re-RW of `ro` entirely. Low priority.

### MEM-04 — `pkey_alloc` failure silently degrades sealing to a no-op (no fatal, no warning)
- **Severity:** Low
- **Type:** Design limitation / defense-in-depth
- **Location:** `h_malloc.c:1256-1258` (`ro.metadata_pkey = pkey_alloc(0, 0);`), consumed at `h_malloc.c:1180-1185` and `memory.c:88-90`
- **Description:** With `CONFIG_SEAL_METADATA` enabled, `init_slow_path` calls `pkey_alloc(0,0)` and stores the result, with no return-value check. On failure `pkey_alloc` returns `-1`. `thread_set_metadata_access` then early-returns when `metadata_pkey == -1` (h_malloc.c:1181), and `memory_protect_rw_metadata` calls `pkey_mprotect(ptr,size,prot,-1)`. Passing pkey `-1` to `pkey_mprotect` behaves like an ordinary `mprotect` (no key assigned), so allocation still works — but the metadata is silently left *unsealed* for the whole process. This can happen if the kernel lacks `CONFIG_X86_INTEL_MEMORY_PROTECTION_KEYS`, if all 15 keys are exhausted, or under seccomp filtering of `pkey_alloc`.
- **Security Impact:** A user who explicitly opted into MPK hardening could silently run with no MPK protection and never know. This is a fail-open of a security feature (though it fails open to the still-strong baseline isolation, not to nothing). No memory-safety impact.
- **Recommendation:** When `CONFIG_SEAL_METADATA` is enabled, treat `pkey_alloc` returning `-1` as `fatal_error` (the user asked for sealing; silently dropping it is surprising), or at minimum emit a one-time warning. Note the graceful-degradation logic at h_malloc.c:1181 is otherwise correct and intentional for the early-init / unsupported path. Low priority because MPK is off by default.

### MEM-05 — MPK is process-global but per-thread; a thread that never calls the allocator API runs with metadata *unsealed*
- **Severity:** Informational
- **Type:** Design limitation (inherent to thread-local PKRU semantics)
- **Location:** `h_malloc.c:1192-1196` (`pkey_set` is per-thread); seal/unseal bracketing at all public entry points (e.g. h_malloc.c:1518-1524, 1721-1740)
- **Description:** `pkey_set`/PKRU is thread-local register state. `hardened_malloc` seals metadata by calling `thread_seal_metadata()` (sets `PKEY_DISABLE_ACCESS`) at the *end* of each public API call and `thread_unseal_metadata()` at the start. A thread is only sealed once it has made at least one allocator call. Threads created before the first allocator call, or that never call into the allocator, have the default PKRU (access enabled) for the metadata key and can therefore freely read/write the metadata region. There is no mechanism (and on Linux, no clean one) to set the PKRU default for all threads at creation.
- **Security Impact:** MPK raises the bar against corrupting metadata *from within a thread mid-allocation-call*, but it is not a process-wide seal: any thread not currently inside an unsealed allocator call still needs to be in the unsealed state to be exploited, and threads that never allocate are simply unsealed. This is the well-understood limitation of using MPK this way and is consistent with how the feature is scoped. It does not undermine the out-of-line isolation, which is the primary defense.
- **Recommendation:** None actionable in userspace today; worth documenting as a known limitation of the MPK feature. The coarse per-call bracketing itself is implemented correctly (see Verified Strengths).

### MEM-06 — `deallocate_pages` failure fallback can leave freed pages mapped read-write with attacker-controlled stale contents
- **Severity:** Low
- **Type:** Defense-in-depth / robustness
- **Location:** `pages.c:85-91`; analogous fallbacks at `h_malloc.c:1022-1025`, `1095-1098`
- **Description:** `deallocate_pages` first tries `memory_unmap`. `memory_unmap` returns the raw `munmap` result and only fatals on non-`ENOMEM` errors (memory.c:60-66). If `munmap` fails with `ENOMEM` (which Linux can return when an unmap would exceed `vm.max_map_count` by splitting a VMA), the code falls back to `memory_purge` (`MADV_DONTNEED`), and if that also fails, to `memset(usable, 0, usable_size)`. In the `ENOMEM` case the mapping remains present and read-write; only its *contents* are zeroed (via purge or memset). The guard pages on either side are not re-established, and the region stays accessible.
- **Security Impact:** Very limited. The contents are reliably zeroed (purge gives zero-filled pages on next touch; memset zeroes in place), so no stale heap data leaks and no UAF-readable secret remains. The residual concern is that the freed region stays mapped RW rather than becoming `PROT_NONE`, so an out-of-bounds access into it would not fault. This only triggers under map-count exhaustion (a pathological, self-inflicted condition that `GUARD_SLABS_INTERVAL` already stresses) and the allocator's own quarantine/region bookkeeping has already removed the region from its tables. No exploitable primitive.
- **Recommendation:** Optionally, on `munmap` `ENOMEM`, attempt `mprotect(PROT_NONE)` before the purge/memset fallback so the region at least becomes inaccessible rather than RW. Low priority; the current behavior is memory-safe and the data-leak vector is already closed by zeroing.

### MEM-07 — `slab_usable_size` is intentionally called outside the unseal/seal bracket; correct, but relies on a non-obvious invariant
- **Severity:** Informational (NOT a bug — verified safe)
- **Type:** Defense-in-depth (documentation/robustness)
- **Location:** `h_malloc.c:775-777`; call sites at `h_malloc.c:1570`, `1858`, `1916`, `1951`
- **Description:** Several public entry points call `slab_usable_size(p)` *after* `thread_seal_metadata()` (e.g. h_malloc.c:1858 in `h_malloc_usable_size`, 1916 in `h_malloc_object_size`) or before `thread_unseal_metadata()` (h_malloc.c:1570 in `h_realloc`). I verified this is safe: `slab_usable_size` only reads `ro.slab_region_start` (in the read-only `ro` page) and indexes the file-scope `static const size_classes[]` table (in `.rodata`). It touches *none* of the MPK-protected `allocator_state`. So under MPK these calls correctly do not fault, and they save a `pkey_set` round-trip. This is a deliberate and correct optimization, not an asymmetry bug.
- **Security Impact:** None. Flagged only because the correctness depends on `slab_size_class`/`slab_usable_size` never being changed to read protected metadata; a future refactor that made them consult `c->size` (which lives in `allocator_state`) would introduce a fault under MPK.
- **Recommendation:** Add a brief comment at h_malloc.c:775 noting these helpers must remain free of protected-metadata access so they can be called while sealed. Documentation only.

### MEM-08 — Re-protection of region hash table on grow failure mirrors MEM-06 (zeroed but left mapped)
- **Severity:** Informational
- **Type:** Defense-in-depth
- **Location:** `h_malloc.c:1095-1101` (in `regions_grow`); `h_malloc.c:1022-1028` (in `regions_quarantine_deallocate_pages`)
- **Description:** After migrating entries to the new hash table, `regions_grow` reclaims the old table by `memory_map_fixed` (re-`PROT_NONE` over it via fresh anonymous mapping). On failure it purges, then `memset`s. Same robustness note as MEM-06: the data is zeroed but, on the `memset` fallback path, the old table pages remain readable/writable. The old table is part of `allocator_state` (so still inside the isolated, guard-wrapped region), and under MPK it is still covered by the pkey because `memory_map_fixed` does not change the pkey assignment of the surrounding VMA region in the success path — but the `memset` fallback leaves stale pointers (region base addresses) momentarily before they are overwritten. They are overwritten with zero, so no stale data persists.
- **Security Impact:** Negligible; the region table only ever holds the allocator's own large-allocation base pointers, which are zeroed. No external data leaks.
- **Recommendation:** None required. Same optional `PROT_NONE`-on-failure suggestion as MEM-06.

## Verified Strengths

The following properties were checked against the code and hold up well:

- **Out-of-line, address-reserved metadata.** All writable allocator state is a single `struct allocator_state` (h_malloc.c:1004-1014) reserved once during init via `allocate_pages(sizeof(allocator_state), metadata_guard_size, false, ...)` (h_malloc.c:1273-1274). The slab region is a separate, single up-front reservation (h_malloc.c:1295). Neither is ever reused for user allocations. *Claim "address space entirely reserved during initialization and never reused" — confirmed.*

- **High-entropy guard regions around metadata, derived from the CSPRNG.** `metadata_guard_size = (get_random_u64_uniform(rng, REAL_CLASS_REGION_SIZE/PAGE) + 1) * PAGE` (h_malloc.c:1270-1271) yields a uniform random guard up to 64 GiB (≈ **24 bits** of entropy), and `allocate_pages` places this guard on **both** sides (`add_guards` adds it twice, pages.c:8-11). The randomness comes from a freshly seeded ChaCha CSPRNG (`random_state_init` → `getrandom`, random.c:27-34; init at h_malloc.c:1264-1268). *Claim "dedicated region with high entropy randomly sized guard regions" — confirmed, and the entropy is genuinely high.*

- **Read-only-after-init globals holding only pointers.** The `ro` union (h_malloc.c:70-85) is page-aligned and padded to a full page (`char padding[PAGE_SIZE]`), then `memory_protect_ro(&ro, sizeof(ro))` after init (h_malloc.c:1332-1334). It contains `slab_region_start`, `slab_region_end` (atomic), the `size_class_metadata[N_ARENA]` pointers, `region_allocator` pointer, `regions[2]` pointers, and (when enabled) `metadata_pkey` — i.e. **all** the pointers an attacker would need to reach writable state. Because these are pointers into a separately-randomized region, leaking the library/`ro` address does not reveal the writable-state address. *Claim "global variables entirely read-only after init with pointers to isolated state" — confirmed; coverage is complete.* The only field that is ever re-RW at runtime is the MTE-disable bool (MEM-03), and that is the documented, narrow exception.

- **Strict `mmap`/`munmap`/`mprotect`/`mremap`/`madvise` error policy.** Every wrapper in memory.c checks the return value and calls `fatal_error` for any errno other than `ENOMEM` (memory.c:20-24, 43-45, 62-64, 74-76, 96-98, 105-107, 114-116). `ENOMEM` is the only recoverable error and is surfaced to callers. *Claim "errors other than ENOMEM treated as fatal" — confirmed for all five syscalls.*

- **Fresh mappings start inaccessible.** `memory_map` maps `PROT_NONE` (memory.c:29-31); `allocate_pages` only unprotects the usable middle and leaves guards `PROT_NONE` (pages.c:19-29). The slab region is mapped once as `PROT_NONE` (via `memory_map_tagged` → `memory_map`, h_malloc.c:1295) and slabs are individually unprotected on first use (`memory_protect_rw(slab, slab_size)` in `alloc_metadata`/`allocate_small`, h_malloc.c:358, 672). The zero-size class (`class == 0`) never unprotects its slab. *Claims "entire slab region starts non-readable/non-writable" and "zero size region remains non-readable and non-writable" — confirmed.*

- **Overflow-safe size/guard arithmetic.** `add_guards` uses `__builtin_add_overflow` twice (pages.c:8-11); `allocate_pages_aligned` checks the alignment-padding addition for overflow (pages.c:40-43, 46-49); `h_calloc` uses `__builtin_mul_overflow` (h_malloc.c:1533); `regions_grow` bounds `total` before doubling (h_malloc.c:1065-1067). The big layout constants (`ARENA_SIZE`, `slab_region_size`, ≈ 2^43.6) are compile-time `static const`/macros, well within `size_t`, and `CONFIG_CLASS_REGION_SIZE` is bounded by `static_assert` (h_malloc.c:48-49, 326). *No integer-overflow or misalignment issue found in page rounding or region sizing.*

- **Initialization is race-safe.** `init_slow_path` takes `init_lock` and re-checks `is_init()` under the lock (double-checked locking, h_malloc.c:1249-1254). `is_init()` reads `slab_region_end` with `memory_order_acquire` (h_malloc.c:87-89, 1235-1237) and the publishing store is `memory_order_release` *after* all of `allocator_state`/`ro` is populated (h_malloc.c:1330). So a concurrent thread either sees the allocator fully initialized or takes the lock. `pthread_atfork` is registered only *after* init completes and the lock is released (h_malloc.c:1337-1342), avoiding a self-deadlock since the handlers allocate. The `constructor(101)` (h_malloc.c:1361-1363) front-runs most user code to set this up early. *No use-before-init window or init TOCTOU found.*

- **Fork safety is correct.** `pthread_atfork(full_lock, full_unlock, post_fork_child)` (h_malloc.c:1340). `full_lock` acquires the region lock and every per-arena/size-class lock before fork (h_malloc.c:1198-1207); `full_unlock` releases them in the parent (h_malloc.c:1209-1218); `post_fork_child` re-initializes all mutexes **and reseeds every CSPRNG** — `random_state_init(&ra->rng)` and `random_state_init(&c->rng)` pull fresh entropy from `getrandom` (h_malloc.c:1220-1233, random.c:27-34). So a forked child cannot deadlock on inherited-locked mutexes and does **not** reuse the parent's random stream. *Fork concerns (lock reset + CSPRNG reseed) — both handled correctly.*

- **MPK seal/unseal bracketing is balanced at the public boundary.** I traced every `thread_unseal_metadata`/`thread_seal_metadata` site (51 sites). The model is: public entry points unseal on entry and seal on **every** return path; helpers that are only reached from already-unsealed contexts do not re-bracket, except `deallocate_large`/`deallocate_small`-adjacent paths where the unseal is performed *inside* `deallocate_large` (h_malloc.c:1424) and the matching seal is at the public caller (h_malloc.c:1739, 1771, 1808) — verified balanced for `h_free`, `h_free_sized`, `h_free_aligned_sized`, `h_realloc`, `h_malloc_usable_size`, `h_malloc_object_size`, `h_malloc_trim`, and the mallinfo family. No path returns while leaving metadata unsealed, and no path accesses protected metadata while sealed (the only post-seal accesses are `slab_usable_size`, which is `.rodata`-only — MEM-07). The early `return old_orig` fast paths (e.g. h_malloc.c:1572) occur *before* the unseal, so they are correctly balanced no-ops.

### Summary verdict

The memory-isolation, guard-region, initialization, and fork-safety implementation is **solid and matches its documented security properties**. The metadata-isolation design (out-of-line state + read-only pointer page + high-entropy bilateral guard regions + reserved-never-reused address space) is implemented correctly and completely, with sound error handling and overflow-safe arithmetic. No memory-safety bug was found in this subsystem. The findings are all either intentional, well-documented tradeoffs (MEM-01 default-off MPK, MEM-02 gap entropy bound), inherent platform limitations of MPK (MEM-05), low-severity fail-open / transient-window hardening notes (MEM-03, MEM-04), or robustness nits in rare `ENOMEM`-on-unmap fallbacks that remain memory-safe because contents are always zeroed (MEM-06, MEM-08). The only changes I would actually recommend are: fatal-on-`pkey_alloc`-failure when MPK is explicitly requested (MEM-04), and a clarifying comment that `slab_usable_size` must stay `.rodata`-only (MEM-07).
